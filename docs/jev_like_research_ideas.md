# Идеи для исследования Jev-like моделей

Рабочие заметки: **исследовательские гипотезы, не утверждения о новизне**. Архитектуры — предварительные варианты, а не зафиксированный дизайн модели. Добавлять самостоятельные идеи в часть I; инфраструктурные оценки и выбор backbone вести отдельно в части III.

## Навигация

- **Часть I — исследовательские идеи:**
  - **Идея 1. Latent reasoning + hidden-state distillation** — варианты A / A+ / A++ / B, включая рекуррентную evidence memory.
  - **Идея 2. MoE decision head** — маршрутизация по вопросу и по варианту; самостоятельная гипотеза, совместимая с идеей 1.
  - **Идея 3. Adaptive Layer Readout** — выбирать информацию не только из последнего слоя backbone.
  - **Идея 4. Pairwise Decision Head** — обучать явное сравнение вариантов между собой.
- **Часть II — общий дизайн исследования:** как проверять гипотезы и сравнивать модели без смешения факторов.
- **Часть III — экспериментальная база и ресурсы:** кандидаты backbone, ориентиры VRAM и стартовая конфигурация под GPU 8 ГБ.

## Часть I. Исследовательские идеи

### Идея 1. Latent reasoning + перенос CoT-представлений в Jev-like

#### 1.1. Замысел

Обычная Jev-like модель читает **контекст, вопрос, варианты** и сразу выдает $P(A), P(B), \ldots$. На задачах, требующих нескольких последовательных логических шагов, такой прямой ответ может уступать LLM, генерирующей Chain-of-Thought (CoT).

**Замысел:** добавить небольшое число *скрытых вычислительных шагов*, после которых по-прежнему сразу выдавать вероятности вариантов — **без генерации текста рассуждения**. Затем попробовать научить эти шаги чему-то полезному с помощью **скрытых представлений обычной LLM после CoT**, а не только её ответов.

**Пример для понимания:** «Брат Алисы — Боб. Боб живёт в Лионе. Где живёт брат Алисы?» Варианты: Париж / Лион / Берлин. Нужно связать «брат Алисы → Боб → Лион». Мы не утверждаем, что нейросеть буквально выполнит эти два шага по очереди; это задача, на которой хотим проверить пользу дополнительных вычислений.

#### 1.2. Вариант A — небольшой рекуррентный модуль поверх LLM

**Идея на пальцах:** LLM один раз «прочитала» весь текст и оставила для каждого токена набор чисел (hidden states). Небольшая голова для каждого ответа несколько раз обращается к этим числам, обновляя своё представление варианта.

```text
Контекст + вопрос ──→ pretrained LLM ──→ H: векторы всех токенов
                                           │
Варианты A, B, C ──→ начальные векторы zA, zB, zC
                                           │
                         повторить 1–4 раза:
                         1) cross-attention: z варианта «смотрит» в H
                         2) маленький MLP + residual: обновить z
                                           │
                         score(zA), score(zB), score(zC)
                                           ↓
                                      softmax → P(A/B/C)
```

**Конкретно по слоям (один возможный набросок):**

- $H \in \mathbb{R}^{T\times d}$ — **не отдельная память**, а выходные векторы токенов LLM; $T$ — длина контекста. Для дешёвой головы можно спроецировать их в меньшую размерность $d_h$.
- $z_A,z_B,z_C\in\mathbb{R}^{d_h}$ — представления вариантов (например, полученные из их текстовых embeddings и вопроса).
- На шаге $t$ считаем $e_i^{(t)}=\operatorname{CrossAttn}(q=z_i^{(t)}, K=H, V=H)$; затем $z_i^{(t+1)}=\operatorname{Update}(z_i^{(t)},e_i^{(t)})$. `Update` — небольшой MLP/гейт с residual и norm.
- **Один и тот же** `CrossAttn + Update` можно применять несколько раз (shared weights). После последнего шага линейный слой выдаёт один logit для каждого варианта.
- В базовой версии варианты **не читают друг друга**: каждый читает общий контекст; только финальный softmax их нормализует. Это сознательный выбор архитектуры, а не универсальное требование Jev-like.

**Почему повторение может помочь:** после первого обращения к контексту $z_B$ изменился; значит, на втором шаге его attention-запрос уже другой и *может* искать другую информацию. Это **не гарантия reasoning**: голова может научиться просто повторять одну операцию. Поэтому обязателен baseline с обычной нерекуррентной головой той же вычислительной стоимости.

**Что переносим:** [End-to-End Memory Networks](https://arxiv.org/abs/1503.08895) — многократные обращения к представлениям входа; [Latent Recurrent Thoughts](https://arxiv.org/abs/2609.01117) — небольшой recurrent-модуль поверх frozen LLM. Ближайший Jev-like ориентир для обычной головы: [OpenJev](https://github.com/ejhshen/OpenJev).

#### 1.3. Вариант A+ — Self-Attention + Cross-Attention непосредственно между вариантами

**Развитие варианта A, не отдельная тема:** попробовать простую decision head, которая одновременно позволяет вариантам взаимодействовать друг с другом и обращаться к исходному контексту. Потенциально использовать её как основу для последующего latent reasoning и дистилляции reasoning от обычной LLM.

**Что уже существует:**
- [Kev](https://github.com/jaredpalmer/kev) — простая Pointer Head: сравнение представления вопроса с представлениями вариантов через обучаемые проекции и dot-product.
- [OpenJev](https://github.com/ejhshen/OpenJev) — Option Set Interactor: взаимодействие между представлениями вариантов перед предсказанием.
- [CLEF](https://huggingface.co/Cloudflare/clef/blob/main/joint_schema_model.py) — Cross-Attention вариантов к контексту, затем Self-Attention + Cross-Attention на уровне вопросов (fields). Архитектура довольно сложная, с дополнительными ветками и несколькими компонентами scoring.
- [Transformer](https://arxiv.org/abs/1706.03762) — комбинация Self-Attention → Cross-Attention → FFN давно известна как стандартный Transformer Decoder Layer.

**Что можно попробовать:**

Простую комбинацию Self-Attention и Cross-Attention **непосредственно на уровне вариантов**, без сложной промежуточной структуры CLEF.

```text
Pretrained GPT backbone
        ↓
Hidden states контекста H [T, d]
Представления вариантов O [K, d]
        ↓
Linear projections
        ↓
┌───────────────────────────┐
│ Self-Attention(O, O, O)   │ ← варианты взаимодействуют
│            ↓              │
│ Cross-Attention(O, H, H)  │ ← обращаются к контексту
│            ↓              │
│ FFN + Residual + Norm     │
└───────────────────────────┘ × N
        ↓
Обновленные варианты [K, d]
        ↓
Общий Linear(d, 1)
        ↓
Softmax по вариантам
```

- Использовать готовые `TransformerDecoderLayer` без causal mask между вариантами.
- Не вводить positional embeddings для порядка вариантов; желательно независимое от перестановки кодирование вариантов в backbone.
- Начать с 1–2 слоёв, без дополнительных scorer-веток.
- Проверить, даёт ли совместная обработка пользу относительно отдельных Self-Attention и Cross-Attention.

**Как превратить эту head в latent reasoning:**

В дальнейшем можно попробовать сделать такой блок рекуррентным: повторять его с общими весами, последовательно обновляя представления вариантов.

Затем исследовать, можно ли с помощью hidden-state distillation от reasoning LLM научить эти итерации выполнять более полезные вычисления.

**Что сравнивать:** Pointer/MLP → только Self-Attention → только Cross-Attention → Self+Cross → рекуррентный Self+Cross. Обязательно учитывать число параметров, FLOPs и latency.

**Новизна:** само сочетание Self-Attention и Cross-Attention не новое. Пока рассматриваем это как простую потенциальную архитектурную основу, а не самостоятельный научный вклад.

#### 1.4. Вариант A++ — Recurrent Evidence Memory (развитие latent reasoning)

**Идея:** дополнить рекуррентную голову A/A+ небольшой **обучаемой рабочей памятью** $E\in\mathbb{R}^{M\times d_h}$ (например, 8–16 слотов). В отличие от векторов вариантов $O$, слоты не привязаны к конкретным ответам: они могут хранить общие промежуточные признаки, полезные для многошагового решения.

```text
Frozen / QLoRA backbone → H [T,d], вопрос q, варианты O [K,d_h]
                                ↓
                       Evidence slots E [M,d_h]
                                ↓
                  ┌── повторить r раз ──┐
                  │ Cross-Attn(E, H)    │ ← память читает контекст
                  │ Self-Attn(E)        │ ← слоты взаимодействуют
                  │ Cross-Attn(O, E)    │ ← варианты читают память
                  │ Update(E), Update(O)│ ← residual / FFN
                  └─────────────────────┘
                                ↓
                       Scoring(O) → softmax
```

- Начальные слоты — обучаемые векторы, желательно **обусловленные вопросом** $q$; повторяемый блок может иметь **общие веса** на всех шагах.
- **Гипотеза:** отдельная память позволяет накапливать сведения, не относящиеся напрямую ни к одному варианту, и полезнее простого повторного обновления только $O$.
- **Не предполагаем**, что отдельные слоты или итерации автоматически соответствуют конкретным логическим шагам.
- **Важная абляция:** доступ вариантов только к $E$ vs доступ ещё и напрямую к $H$ — маленький bottleneck может терять факты; ускорение не гарантируется.
- **Что сравнить:** recurrent A+ без памяти → однократное извлечение $E$ → recurrent $E$ (шаги $r=1,2,4$), с контролем числа параметров/FLOPs. Затем при необходимости — hidden-state distillation для итогового агрегированного состояния памяти.
- **Откуда идея:** [Perceiver](https://arxiv.org/abs/2103.03206) — латентный bottleneck; [End-to-End Memory Networks](https://arxiv.org/abs/1503.08895) — многократное чтение памяти. **Сам механизм не новый**; интересно проверить именно отдельную *рекуррентную* рабочую память в Jev-like decision head.

#### 1.5. Вариант B — непрерывные latent tokens внутри самой LLM (Coconut)

**Идея на пальцах:** вместо отдельной маленькой головы используем уже обученные слои самой LLM. Она читает вопрос, после чего делает ещё 1–4 шага **без выбора текстовых токенов**: получившийся hidden vector подаём как embedding следующего шага.

```text
Контекст + вопрос + варианты
             ↓
        LLM: обычный prefill
             ↓
       последний hidden h0
             ↓
       LLM(embedding = h0) → h1   # новый latent token
             ↓
       LLM(embedding = h1) → h2
             ↓
       ... (1–4 шага)
             ↓
       Decision readout → logits вариантов → softmax
```

**Что технически происходит:**

- При инференсе LLM сначала обрабатывает обычные текстовые токены; их $KV$-cache сохраняется.
- Затем обрабатывается **одна новая позиция** с `inputs_embeds`, куда подаётся проекция предыдущего hidden state; это *не* преобразование в token ID и *не* генерация слова.
- На каждом таком шаге выполняются **все слои LLM для нового латентного токена**, с доступом к предыдущему контексту через cache. Исходный текст заново не прогоняется, но шаг дороже, чем итерация маленькой головы из варианта A.
- После последнего шага получаем вектор $h_r$. Decision readout сравнивает его с векторами текстовых вариантов и формирует logits $A/B/C$ (или другой специализированный readout — пока открыто).
- Для обучения градиент должен проходить через латентные шаги; cache-оптимизации инференса **не следует автоматически переносить** на training-код.

**Чем отличается от A:** в A повторяется дешёвый `CrossAttn + MLP` *вне* LLM; в B несколько раз последовательно работает **сама LLM**, но только над новым латентным токеном. В обоих случаях финальный ответ не генерируется как текст.

**Что переносим:** [Coconut / Chain of Continuous Thought](https://arxiv.org/abs/2412.06769) — hidden state в качестве embedding следующего «мысленного» шага; [CODI](https://aclanthology.org/2025.emnlp-main.36/) — continuous thoughts и их обучение. Отдельно важно сравнивать с [SanSi](https://arxiv.org/abs/2610.07730): он использует looping backbone для typed decisions, но это не то же самое, что инкрементальные latent tokens с cache.

#### 1.6. Дополнительный способ обучения A/A+/A++/B — hidden-state distillation от CoT

Сначала все варианты можно обучать **обычным CE на правильном варианте**, без учителя. Дальше проверять, добавляет ли что-нибудь перенос информации от LLM, которая действительно сгенерировала рассуждение.

```text
TEACHER (только при подготовке сигналов):
вопрос + варианты → обычная reasoning LLM → текст CoT →
скрытый вектор h_T в позиции непосредственно перед ответом
                                                │
                                                │ сигнал для обучения
                                                ↓
STUDENT:
тот же вопрос + варианты → архитектура A / A+ / A++ / B →
конечный вектор z_S → decision logits → P(A/B/C)
```

**Что именно предлагаем сравнить:**

1. **Без дистилляции:** только $L_{\mathrm{CE}}$ по правильному ответу.
2. **Output distillation:** дополнительно учить повторять $P_T(A/B/C)$ учителя *после* CoT; это уже исследовано в Jev-like и нужно как baseline.
3. **Hidden-state distillation:** выбрать информативный вектор учителя *после* CoT (например, состояние перед токеном ответа), и мягко сопоставлять с финальным состоянием студента через небольшую проекцию: $L=L_{\mathrm{CE}}+\lambda L_{\mathrm{align}}(Wz_S,\operatorname{stopgrad}(h_T))$.

Для A/A+ $z_S$ — ещё не зафиксированный **общий вектор решения** (например, pooled представление вариантов или отдельный readout-query); для A++ — агрегированное состояние рабочей памяти или вариантов; для B — последний непрерывный thought-vector. **Не нужно** искусственно сопоставлять 1-й шаг CoT с 1-й итерацией студента: такой естественной пары нет.

**Главная проверка:** даёт ли вариант 3 прирост относительно **той же архитектуры без alignment** и относительно дистилляции **только выходных вероятностей**? Если нет — hidden-state alignment не оправдан. Не предполагаем заранее, что буквальный MSE между чужими представлениями окажется лучшим способом.

#### 1.7. Эксперименты и критерии результата

- **Основное:** accuracy на задачах с несколькими логическими шагами при фиксированном времени/FLOPs; отдельно график accuracy по числу latent steps $r=0,1,2,4$.
- **Контроли:** обычная Jev-like голова; более глубокая **нерекуррентная** голова сопоставимого размера/стоимости; архитектуры A/A+/A++/B без учителя; output-only distillation; reasoning-LLM с CoT как более дорогой ориентир.
- **Дополнительно:** Brier/ECE (вероятности не должны деградировать), latency; желательно отдельно посмотреть вопросы с одним и несколькими необходимыми логическими переходами.
- **Для первой проверки:** задачи multiple-choice с размеченными ответами, где нужен не только фактологический recall (например, ARC-Challenge, ReClor; при выборе проверить сложность и наличие подходящего train split). Масштаб и точный датасет пока не фиксируем.

Архитектурная комбинация — гипотеза для исследования, а не заявленная новизна.

### Идея 2. Mixture of Experts (MoE) внутри decision head

**Зачем:** одна универсальная Jev-like модель решает разные задачи (классификация, NLI, выбор действия, оценка качества), а единая head может испытывать *negative transfer*: обновления, полезные для одной задачи, мешают другой. Попробовать несколько небольших **совместно обучаемых экспертов** вместо одной плотной головы; роутер решает, как их комбинировать **без ручной разметки типов задач**.

**Базовая схема:** `GPT backbone → (возможно, latent reasoning из идеи 1) → MoE decision head → K logits → softmax`. MoE не заменяет reasoning и **может добавляться независимо или после него**.

#### 2.1. Вариант A — Question-level routing

Для каждого вопроса роутер получает общий вектор $q\in\mathbb{R}^{d}$, выдаёт веса экспертов $w(q)\in\mathbb{R}^E$. Каждый эксперт оценивает **весь набор вариантов** этого вопроса; их logits объединяются с одинаковыми весами:

```text
                  Вопрос q + варианты [K,d]
                             ↓
                    Router(q) → [E]
                             │
             ┌───────────────┼──────────────┐
             ↓               ↓              ↓
         Expert 1         Expert 2       Expert 3
         logits [K]       logits [K]     logits [K]
             └───────────────┼──────────────┘
                             ↓
                Взвешенная сумма [K]
                             ↓
                          Softmax
```

- $s_i=\sum_{e=1}^{E}w_e(q)\,s_{e,i}$ — один вес эксперта действует на все варианты вопроса.
- Эксперт — **MLP scorer** или маленькая `Self-Attention → Cross-Attention → FFN` head; все эксперты видят одни и те же представления.
- Разные вопросы к одному контексту могут использовать **разные смеси экспертов**. Это не per-token MoE внутри LLM.

#### 2.2. Вариант B — Option-level routing

Роутер получает **пару** `[q; o_i]` и отдельно определяет веса экспертов **для каждого варианта**. Параметры экспертов и роутера общие для всех вариантов; **коэффициенты смешивания различаются для каждого варианта**:

```text
                   q + варианты [oA, oB, oC]
                              ↓
               Router([q,oA]), Router([q,oB]), ...
                              ↓
                  веса [K,E] для экспертов
                              ↓
             каждый эксперт оценивает варианты
                              ↓
                смесь оценок для каждого i
                              ↓
                         Softmax
```

- $s_i=\sum_{e=1}^{E}w_e(q,o_i)\,s_e(q,o_i)$ — у A и B могут быть **разные маршруты**, даже если это варианты одного вопроса.
- Простая реализация: эксперты — небольшие общие MLP-scorers для пары `[q; o_i]`. Для внимания между вариантами/контекстом можно сначала получить общие уточнённые $o_i$, а затем применять option-level MoE к scorer либо FFN.
- **Проверяемое отличие:** маршрутизация на уровне вопроса специализирует обработку целой задачи; на уровне варианта — обработку отдельных гипотез. Второй вариант гибче, но потенциально хуже согласует масштабы logits.

#### 2.3. На что опираемся и что уже пробовали

- **[MMoE (KDD 2018)](https://doi.org/10.1145/3219819.3220007)** — эксперты с обучаемыми gates для многозадачного обучения; исходная мотивация — уменьшение negative transfer. Идея маршрутизации и совместного обучения **сама по себе не новая**.
- **[layaMOE](https://github.com/vishalmysore/layaMOE)** — близкая Jev-like реализация: общий **замороженный ModernBERT**, отдельные **доменные копии decision head** и router, который выбирает **одну голову на запрос** (hard routing по виду текста). Есть также обучаемый роутер на pooled hidden states. Авторы приводят 59,6% → 67,3% на 312 ответах, но датасет небольшой и результаты не доказывают превосходство любой MoE-head.
- **[Kev](https://github.com/jaredpalmer/kev), [OpenJev](https://github.com/ejhshen/OpenJev), [CLEF](https://huggingface.co/Cloudflare/clef/blob/main/joint_schema_model.py)** — ориентиры для плотных (non-MoE) decision heads и их механизмов обработки вариантов.

**Что отличается в нашей постановке от layaMOE:** **GPT-like backbone + QLoRA**, совместное обучение роутера и экспертов на разнообразных задачах, *soft routing по каждому вопросу* либо *по каждому варианту*, без заранее заданных доменных экспертов. Это **гипотезы для экспериментов, а не подтверждённая новизна**.

#### 2.4. Первый эксперимент

Сравнить на **одних данных и backbone**: обычную dense head → question-level MoE → option-level MoE. Для начала 3–4 небольших MLP-эксперта и soft routing, затем при наличии смысла заменить экспертов на attention-блоки или рассмотреть top-k routing. Обучение: общий CE по правильному варианту, при необходимости контроль дисбаланса использования экспертов.

**Метрики:** accuracy по отдельным типам задач и в среднем; качество на незнакомых типах/доменах; Brier/ECE, latency. **Обязательно** сравнить с плотной головой сопоставимого **числа параметров и FLOPs**: иначе эффект MoE легко спутать с простым увеличением capacity. Отдельно проверить, не схлопнулся ли router в одного эксперта.

**Как сочетается с идеей 1:** `Backbone → latent steps → MoE Head` — самый простой вариант независимого добавления; другой вариант — MoE-FFN внутри повторяемого latent-блока. Комбинировать **после** проверки самостоятельного выигрыша каждой идеи.

### Идея 3. Adaptive Layer Readout — извлекать признаки из разных слоёв LLM

**Мотивация:** обычно Jev-like head использует последние hidden states backbone, хотя для разных задач полезная информация может находиться **на разных глубинах** LLM. Последний слой оптимизирован прежде всего под задачу предобучения и не обязан быть лучшим для каждого decision readout.

**Что попробовать:** взять представления нескольких слоёв $H_{l_1}, H_{l_2}, H_{l_3}\in\mathbb{R}^{T\times d}$ и обучить небольшую сеть выбирать их смесь **в зависимости от вопроса**:

$$
H_{\mathrm{mix}}=\sum_j\alpha_j(q)H_{l_j},\qquad \alpha(q)=\operatorname{softmax}(\operatorname{MLP}(q)).
$$

```text
          Pretrained LLM (frozen)
            ├── H_early ─┐
            ├── H_mid ───┼── Adaptive mixing по q → H_mix
            └── H_last ──┘                         ↓
                                            Decision head
                                                ↓
                                               Scores
```

- **Базовые сравнения:** только последний слой → статическая обучаемая смесь → **question-conditioned** смесь. Одинаковая голова и backbone.
- **Гипотеза:** зависимость весов от вопроса улучшит универсальность на разных типах задач без существенного усложнения головы.
- **Практически:** отлично подходит для frozen backbone; начать с 3–4 слоёв, но кэш нескольких $H_l$ увеличивает объём данных на диске.
- **Откуда идея:** [ELMo](https://arxiv.org/abs/1802.05365) — обучаемое смешивание представлений разных слоёв языковой модели; условное по вопросу смешивание для Jev-like — **исследовательская гипотеза, не заявленная новизна**.

---

### Идея 4. Pairwise Decision Head — явно сравнивать варианты друг с другом

**Мотивация:** выбор правильного ответа часто **относителен**: среди нескольких семантически близких вариантов нужно выбрать наиболее точный. Обычный scorer оценивает каждый вариант, а Self-Attention лишь неявно моделирует их взаимодействие.

**Что попробовать:** обучать небольшую **парную функцию предпочтения** $g(q,o_i,o_j)$, а затем агрегировать результаты сравнений в logits:

$$
a_{ij}=g(q,o_i,o_j)-g(q,o_j,o_i),\qquad
s_i=\frac{1}{K-1}\sum_{j\neq i}a_{ij},\quad K\geq2.
$$

```text
Context / Question + Options [K,d]
               ↓
       Pairwise comparator
               ↓
     A vs B, A vs C, B vs C
               ↓
       Aggregate → [K] logits
               ↓
              Softmax
```

- Антисимметричная разность обеспечивает $a_{ij}=-a_{ji}$; обучать можно обычным CE по правильному варианту, без отдельных парных меток.
- **Гипотеза:** явное сравнение повысит точность на вопросах с близкими или частично правильными distractors.
- **Что сравнить:** независимый MLP/Pointer scorer → Self-Attention head → Pairwise head при сопоставимых параметрах/FLOPs; отдельно оценить зависимость от числа вариантов и перестановок.
- **Ограничения:** $O(K^2)$ пар, возможные противоречивые предпочтения, необходимость проверить калибровку итогового softmax.
- **Откуда идея:** [RankNet / Learning to Rank](https://www.microsoft.com/en-us/research/publication/learning-to-rank-using-gradient-descent/) — парное ранжирование давно известно. **Новизна не в pairwise scoring как таковом**, а потенциально в его пользе относительно сильных Jev-like heads.

## Часть II. Общий дизайн исследования

**Цель:** доказать пользу конкретного изменения Jev-like архитектуры при прочих равных, а не обязательно превзойти существующие модели с другими backbone, данными и обучением.

**Основной подход:** сначала дешёво исследовать архитектуру головы с полностью замороженным backbone, затем подтвердить наиболее перспективные результаты при совместном обучении головы и QLoRA.

### Этап 1. Frozen backbone — поиск и проверка гипотез

```text
                Pretrained LLM
              (frozen, 4-bit)
                      ↓
                 Hidden states
                      │
            ┌─────────┼─────────┐
            ↓         ↓         ↓
        Dense Head  MoE Head  Recurrent Head
            │         │         │
            └─────────┼─────────┘
                      ↓
                   Compare
```

- **Backbone полностью заморожен:** никаких LoRA-адаптеров, backward выполняется только через обучаемую голову.
- Можно взять более крупную LLM (**4B, потенциально 7–8B**), поскольку не нужно хранить активации backbone для его обучения.
- **Кэширование hidden states:** для фиксированного датасета один раз прогнать backbone и сохранить представления контекста, вопросов и вариантов. Далее независимо обучать разные головы без повторных запусков LLM.
- Каждую архитектуру головы обучать **с нуля**, используя одинаковые закэшированные представления, train/validation/test split и сопоставимый бюджет обучения.
- Сравнивать не только с простой головой, но и с **Dense Head сопоставимого размера и вычислительной стоимости**.
- Можно относительно дёшево исследовать несколько архитектур, гиперпараметров и random seeds.

**Важно:** это полноценная экспериментальная постановка — исследование decision heads на фиксированных представлениях pretrained LLM. Но полученный выигрыш **не гарантирует**, что он сохранится при QLoRA.

**Ограничение для latent reasoning:** подход особенно удобен для рекуррентных модулей **поверх** готовых hidden states. Если латентные шаги выполняются **внутри LLM** (Coconut-подобный вариант), простого кэширования недостаточно: нужны дополнительные прогоны backbone, а при обучаемых входах латентных шагов — градиенты через его вычисления, даже если сами веса заморожены.

### Этап 2. QLoRA — подтверждение результата

Если модификация показывает устойчивый выигрыш на frozen backbone:

```text
              Pretrained LLM
                     │
           ┌─────────┴─────────┐
           ↓                   ↓
      QLoRA + Dense       QLoRA + Proposed
           │                   │
           ↓                   ↓
       Независимое          Независимое
        обучение             обучение
           │                   │
           └─────────┬─────────┘
                     ↓
                  Compare
```

- Обе модели стартуют с **одинакового исходного pretrained backbone**.
- Обе головы обучаются независимо, с собственной начальной инициализации.
- Одинаковые данные, QLoRA-конфигурация, оценочный протокол и сопоставимый бюджет обучения.
- Проверяем, сохраняется ли выигрыш нового модуля при адаптации представлений самого backbone.
- Для этого этапа можно использовать **меньшую модель 3–4B**, если 7–8B с QLoRA не помещается на GPU.

**Не использовать замену головы в уже обученном checkpoint как основное доказательство архитектурного преимущества:** это другая задача — post-hoc адаптация готовой модели.

### Общие требования к экспериментам

- **Baseline:** простая, но адекватная Jev-like голова; дополнительно — более сильная Dense Head.
- **Контроль сложности:** число параметров, активные параметры, FLOPs и latency. Для MoE особенно важно не спутать пользу маршрутизации с простым увеличением модели.
- **Абляции:** проверять изменения по отдельности; комбинировать идеи только после оценки их самостоятельного эффекта.
- **Надёжность:** несколько датасетов/типов задач, несколько random seeds для основных сравнений, среднее и разброс результатов.
- **Метрики:** accuracy, при необходимости Brier/ECE; отдельно скорость, VRAM и стоимость инференса.
- **Переносимость:** желательно проверить основной результат хотя бы на втором backbone или другой базовой голове.
- **Внешнее сравнение:** Kev, OpenJev, CLEF и другие Jev-like модели — полезные ориентиры, но прямое сравнение accuracy моделей с разными backbone и обучением само по себе не доказывает пользу нашего модуля.

**Минимальная логика доказательства:**

1. `Frozen backbone + Dense Head` vs `Frozen backbone + Proposed Head` — дешёвая архитектурная проверка.
2. Сравнение с более крупной Dense Head — контроль числа параметров и вычислений.
3. `QLoRA + Dense Head` vs `QLoRA + Proposed Head` — проверка при совместной адаптации backbone.
4. По возможности второй backbone — проверка переносимости.

**Принцип:** не тратить ресурсы на полное QLoRA-обучение каждой гипотезы. Сначала отобрать перспективные варианты с frozen backbone, затем подтвердить результат более дорогими экспериментами.

## Часть III. Экспериментальная база и ресурсы

### Основная конфигурация: GPU 8 ГБ (RTX 5050)

Рассматриваем два режима:

| | Frozen backbone | QLoRA |
|---|---|---|
| Что обучается | Только decision head | Head + LoRA-адаптеры |
| Backbone | Желательно 4-bit | NF4 4-bit |
| Backward через backbone | Нет* | Да |
| Память под активации backbone | Минимальная | Существенная |
| Кэширование hidden states | Да, для фиксированных входов | Нет, если обучаются LoRA |
| Реалистичный размер модели | **4B комфортнее; 7–8B пробовать** | **3–4B** |
| Основная роль | Поиск и проверка архитектур | Подтверждение результата |

\* Для обычной головы поверх выходных hidden states. Если обучаемый модуль взаимодействует с внутренними вычислениями backbone, ситуация может отличаться.

### Оценка памяти

**Пример крупной decision head:**

- Проекция из hidden size backbone в 512.
- 4 блока `Self-Attention → Cross-Attention → FFN`.
- FFN width 2048.
- Около **20–21 млн обучаемых параметров**.
- FP32 + AdamW: около **320 МиБ** на параметры, градиенты и состояния оптимизатора, без активаций.

Для MoE память зависит от количества экспертов. Если каждый эксперт — полноценная копия такой головы, расход быстро возрастает. На первом этапе предпочтительнее небольшие эксперты.

**Ориентировочная память под frozen backbone в 4-bit:**

| Размер backbone | Ориентир VRAM под модель | Практическая оценка на 8 ГБ |
|---|---:|---|
| 3B | ~1,8–2,8 ГБ | Комфортно |
| **4B** | **~2,4–3,7 ГБ** | **Основной рабочий диапазон** |
| 7B | ~4,0–5,8 ГБ | Реалистично, но меньше запас |
| **8B** | **~4,7–6,5+ ГБ** | **Пробовать; не гарантировано** |

Это **приблизительные ориентиры размещения модели**, не измеренный peak VRAM. Итоговое потребление дополнительно включает голову, активации, временные буферы CUDA и накладные расходы фреймворка.

Особенно для 7–8B важно не загружать ненужную `lm_head` с проекцией на весь словарь: для Jev-like достаточно hidden states языкового backbone. Неиспользуемая выходная проекция может занимать значительный объём памяти.

**Предварительный вывод:**

- **4B + frozen backbone + крупная FP32-head** — реалистичная и относительно удобная конфигурация.
- **7–8B + frozen 4-bit backbone** — потенциально доступны, особенно при context length 1–2K и небольшом microbatch; 4K нужно проверять.
- **7–8B + QLoRA + крупная head** — для 8 ГБ уже нежелательная основная конфигурация.
- Увеличение размера frozen backbone не требует переобучения его весов, но увеличивает время первичного извлечения hidden states.

### Кэширование представлений

```text
Датасет
   ↓
Frozen 4-bit LLM
   ↓
Hidden states контекста и вариантов
   ↓
Сохранение в FP16/BF16 на диск
   ↓
Обучение различных heads
без повторных прогонов LLM
```

- Особенно выгодно, если планируется много архитектурных экспериментов на одном датасете.
- После извлечения представлений **backbone можно вообще выгрузить из VRAM** и обучать только головы.
- Ограничение — размер кэша. Например, 5000 последовательностей по 2048 токенов с hidden size 4096 потребуют около **78 ГиБ** при сохранении всех токенных hidden states в FP16.
- Можно хранить представления частями, использовать memory-mapped файлы или уменьшать длину контекста.
- Кэш действителен для конкретного способа формирования входов: изменения prompt, порядка вариантов, attention mask или backbone требуют пересчёта соответствующих представлений.

### Потенциальные backbone-модели

**Критерии выбора:**

- Хорошие исходные способности на reasoning и других decision-задачах.
- Возможность получать token-level hidden states.
- Поддержка 4-битной загрузки и стандартного PyTorch/Transformers.
- Желательно обычный decoder Transformer, если планируются нестандартные attention masks и независимые ветки вопросов.
- Возможность использовать тот же backbone с QLoRA на втором этапе — преимущество, но не обязательное условие.

- **[Qwen3-1.7B](https://huggingface.co/Qwen/Qwen3-1.7B)** — облегчённый вариант для первичной отладки, не основной кандидат по качеству.

**Важно:** более крупный или более новый backbone не обязательно лучше именно для Jev-like readout. Качество скрытых представлений на выбранных задачах необходимо проверять экспериментально.

### Предварительный план использования моделей

**Этап 1 — frozen:**

- Начать с `Qwen3-4B-Instruct-2507` или `Granite 4.2-3B`.
- Использовать 4-bit backbone и полностью обучаемую head.
- Извлечь и закэшировать hidden states.
- Провести сравнения Dense / Self+Cross / MoE / Recurrent и необходимые абляции.
- Для перспективных архитектур дополнительно попробовать **Granite 4.2-8B** или **Qwen3-8B**, если пройдут memory-тест.

**Этап 2 — QLoRA:**

- Использовать `Granite 4.2-3B` или `Qwen3-4B-Instruct-2507`.
- NF4 QLoRA, rank 8–16, gradient checkpointing.
- Начать с context length **2K**, затем проверять **4K**.
- Microbatch **1**, effective batch **16–32** через gradient accumulation.
- Независимо обучить baseline и наиболее перспективную модификацию от одинакового pretrained backbone.

**Проверка ресурсов:**

- Для frozen: измерить peak VRAM на полном `backbone forward → head forward → head backward → optimizer.step()`.
- Для QLoRA: измерить полный `forward → backward → optimizer.step()` с градиентами через backbone.
- Отдельно замерить время извлечения hidden states, размер кэша и скорость обучения головы.
- Использовать `torch.cuda.max_memory_reserved()` и фактические времена шагов, а не только теоретический размер 4-битных весов.

**Итоговая стратегия:** основную часть архитектурных экспериментов проводить с **frozen 4B**, при возможности дополнительно проверить **frozen 7–8B**. Полноценное QLoRA-обучение **3–4B** оставить для подтверждения наиболее перспективных результатов.

Так можно существенно сократить вычислительный бюджет, не отказываясь от методологически корректных сравнений.
