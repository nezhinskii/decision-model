# Технические договорённости по исследовательскому репозиторию Jev-like моделей

**Статус:** согласованная основа для реализации · **Дата:** 18.10.2026  
**Адресат:** агент-разработчик. Этот документ описывает цели, принятые решения, ограничения и ожидаемые свойства системы. Он **не** задаёт детальную реализацию классов, формат каждого файла или готовые API: такие решения следует принимать по ходу работы, не усложняя проект без необходимости.

## 1. Назначение проекта и общий подход

Репозиторий нужен для **исследования Jev-like decision-моделей**, а не для немедленной сборки одной максимально качественной модели. Основная задача — независимо проверять архитектурные гипотезы на сопоставимых данных, затем при необходимости объединять удачные компоненты.

Основные направления, описанные подробнее в отдельных исследовательских материалах:

- Простые **Pointer / Dense heads** как контрольные модели.
- **Joint Latent-Option Head:** совместная обработка вопроса, вариантов и дополнительных обучаемых латентных слотов; при необходимости Cross-Attention к токенным представлениям контекста.
- **Question–Option MoE Head:** маршрутизация в экспертов при обработке вопроса и вариантов.
- **Adaptive Layer Readout:** использование представлений вопроса и вариантов с нескольких слоёв LLM.
- **Recurrent Head:** повторяемые шаги обработки, потенциально в составе Joint-архитектуры.

**Исследовательская последовательность:**

1. **Frozen backbone:** предобученная LLM заморожена; извлекаем и по возможности кэшируем hidden states; обучаем только голову / readout. Это основной дешёвый режим для абляций.
2. Сравниваем с адекватными простыми baseline, проводим абляции и проверки устойчивости результата.
3. **QLoRA:** для перспективных конструкций независимо обучаем LoRA-адаптеры вместе с соответствующей головой и сравниваем с контрольной архитектурой при сопоставимом бюджете.
4. Только после проверки отдельных гипотез экспериментируем с их комбинациями; публикация моделей и более широкие бенчмарки — следующие этапы.

**Ресурсное ограничение:** основная машина — **NVIDIA RTX 5050, 8 ГБ VRAM**. Поэтому нужно экономно обращаться с памятью GPU, не держать большой backbone загруженным без необходимости и переиспользовать дорогостоящие извлечённые признаки. Не предполагать, что конкретный QLoRA-режим помещается в 8 ГБ без реального теста полного forward/backward.

## 2. Репозиторий, окружение и способ запуска

- **Обычный модульный Python-пакет** с исходниками в `src/jev_research/`. Предпочтительны небольшие компоненты с ясной ответственностью, а не монолитный скрипт или заранее спроектированный универсальный фреймворк.
- **`uv`** для создания окружения, зависимостей и запуска команд. Фиксировать зависимости в `uv.lock` и коммитить lockfile в Git.
- **PyTorch с CUDA** — явно выбранная совместимая сборка из индекса PyTorch, зафиксированная в зависимостях. Сам `uv` не устанавливает системный драйвер NVIDIA. Конкретные версии Python/PyTorch/CUDA сверить с реальной машиной; **Python 3.11 — предварительный ориентир**, а не требование любой ценой.
- Если кэш пакетов `uv` и `.venv` расположены на одной совместимой файловой системе, можно использовать **hardlink** для экономии диска на крупных пакетах (например, PyTorch). Не считать это обязательным для работы проекта.
- **Ноутбуки** (`notebooks/`) — для исследования, графиков, разбора ошибок, демонстраций. Основные процессы подготовки данных, извлечения признаков, обучения, evaluation и benchmark должны вызываться из обычного Python-кода/CLI.
- Долгие обучения и прогоны — **отдельные процессы**, а не состояние живого Jupyter kernel: это помогает освобождать VRAM и воспроизводить запуск.
- **`tests/`** для проверок корректности; **`artifacts/`** (или аналогичный каталог) — локальные генерируемые результаты, исключённые из Git. Крупные кэши и checkpoints не коммитить.

Ориентир для структуры — **не требование к точным именам файлов**:

```text
src/jev_research/
    data/              # источники, нормализация, фиксированные выборки, батчи
    backbone/          # LLM, кодирование входов, внимание, позиции, extraction
    features/          # единый формат признаков, кэш и разрешение cache/compute
    models/
        readouts/      # выбор/смешивание представлений слоёв
        heads/         # Pointer, Joint, MoE, Recurrent и др.
    training/          # training loop, оптимизация, checkpointing
    evaluation/        # оценка и benchmark
    ...                # конфиги, сборка моделей, CLI, MLflow-интеграция
notebooks/
tests/
artifacts/              # локально, не в Git
pyproject.toml
uv.lock
```

Не создавать все директории и абстракции «на будущее»: развивать структуру по мере появления реальной функциональности.

## 3. Конфигурации, CLI и воспроизводимость

**Выбранная схема:** типизированные Python **`dataclass` + `tyro`** для CLI, без Hydra и без обязательных YAML-конфигов.

- Конфигурации отделены от `nn.Module`: они описывают backbone, состав модели, параметры обучения, данные, кэш и оценку.
- Для альтернативных архитектур использовать типизированные варианты конфигураций; структура допускает вложенные компоненты.
- Каждый настоящий запуск сохраняет **полную разрешённую конфигурацию** (включая значения по умолчанию) в JSON, а не только переданные CLI-аргументы.
- Для обратного чтения JSON в типизированные dataclass можно использовать **Pydantic `TypeAdapter`** и различение вариантов по полю типа. Не писать собственный ручной JSON-парсер, если штатной типизированной десериализации достаточно.
- Конфиг **описывает** модель; отдельная небольшая фабрика/сборщик **создаёт** нужные `nn.Module`. JSON не создаёт Python-модель автоматически. Не реализовывать сложную динамическую систему плагинов ради этого.
- Сохранять привязку к **Git commit**, сведения о незакоммиченных изменениях (если есть), версиям зависимостей/окружения, seed, точным ревизиям backbone/tokenizer, версии датасета, split и конфигурации экстракции/кэша.
- **Старые эксперименты не обязаны открываться новой версией кода.** Для воспроизведения старой архитектуры можно вернуться на её Git-коммит с соответствующим lockfile, конфигурацией и данными. Не поддерживать бесконечные миграции конфигов «про запас».

## 4. Данные: первый исследовательский протокол

На первом этапе **не нужно максимизировать качество за счёт огромного датасета**: нужны дешёвые, честные, сопоставимые абляции.

**Основной кандидат:** [OpenJevData-140k](https://huggingface.co/datasets/shenjunhao/OpenJevData-140k). В нём разнообразные decision-задачи, включая reasoning; **это предварительный выбор**, требующий проверки состава, качества, длин и повторов. Его исходные категории/этапы `SFT` и `RL` **не считать готовыми train/validation/test** для нашего исследования. Другие источники (например, данные Kev) можно добавить позднее, если обоснованно нужны.

**Текущий рабочий ориентир для `research_v1`:**

| Разбиение | Примерный размер | Использование |
|---|---:|---|
| `train` | **6 000** | обучение |
| `validation` | **2 000** | выбор checkpoints, абляции, подбор гиперпараметров |
| `test` | **2 000** | редкое независимое подтверждение выбранного решения |
| **Всего** | **10 000** | |

Внутри `train` предусмотреть **фиксированные вложенные подвыборки 1k / 3k / 6k**: smoke/pilot/data-scaling и основные сравнения. Размеры — **не жёсткий предел**: перед фиксацией проверить категории, распределение числа вариантов, token lengths и стоимость кэша; если данных мало для сложных задач, корректировать обоснованно. Ранее обсуждавшиеся 20k — не обязательный объём.

**Разбиения должны быть воспроизводимы:**

- Фиксировать исходный dataset revision, выбранные **ID примеров** и manifest разбиения; одного случайного seed недостаточно.
- Контролировать пропорции категорий и типов задач, в особенности multi-hop/deductive reasoning и задач, полезных для наших гипотез.
- Исключать дубли и пересечения **по исходным задачам/контекстам/шаблонам**, а не только побайтово одинаковые строки. При необходимости группировать взаимосвязанные примеры до split; не допускать утечки одного исходного контекста между train/val/test.
- Сохранять метаданные источника и категории примера; унифицировать формат вопроса, контекста, вариантов и ответа. Поддерживать **переменное число вопросов и вариантов** и, где присутствуют, **soft targets**, а не только жёсткую правильную метку.
- Зафиксированный `research_v1` **не менять задним числом**; существенные изменения — новая версия набора.

**Правила сравнения:**

- Основные абляции — одинаковые исходные данные, split, backbone, формат входа и сопоставимый бюджет оптимизации; не сравнивать без оговорок результаты с разных `pilot`/`research`-режимов.
- Validation можно использовать часто; **test не использовать для выбора архитектуры или гиперпараметров**. Публичные бенчмарки на первом этапе необязательны; позже они потребуются для оценки переноса и сопоставления с внешними моделями.
- Логировать не только общий `accuracy`, но и качество **по категориям**. При soft targets оценивать качество предсказанных распределений (например, loss/Brier), а не только accuracy.
- Перспективные различия перепроверять на нескольких seeds и по возможности на других задачах/backbone. При первых экспериментах полезна небольшая кривая качества на 1k/3k/6k для Pointer и одной сложной головы, прежде чем увеличивать train.

## 5. Backbone, формирование входов, attention и позиции

**Первый кандидат backbone** — замороженный **Qwen3-4B-Instruct-2507**, при необходимости в 4-bit для экономии VRAM; как запасные варианты изучаются другие модели. Для этой Qwen в исследовательских материалах используется `hidden_size=2560`, 36 слоёв. **Это стартовый экспериментальный выбор, а не намертво заданная поддерживаемая модель.**

У всех архитектур должен быть **один согласованный механизм подготовки входа и извлечения признаков** — иначе сравнения не будут честными.

Для задач с общим контекстом, несколькими вопросами и вариантами:

- Общий контекст доступен соответствующим вопросам и вариантам.
- Вопрос и его варианты **не видят чужие вопросы и варианты**.
- Внутри текстовых блоков сохраняется причинная (causal) структура внимания.
- **По умолчанию варианты одного вопроса независимы**: каждый видит контекст и свой вопрос, но не другие варианты. Это позволяет изучать взаимодействие вариантов именно в decision head.
- **Альтернативный режим — последовательные варианты**: следующий вариант может видеть предыдущие варианты **своего** вопроса. Конфигурируемый вариант для сравнения; учитывать возможную зависимость от порядка вариантов.
- Для независимых веток логичны согласованные **ветвящиеся `position_ids`**: после общего префикса позиции каждого варианта начинаются одинаково; для последовательного режима продолжаются последовательно. Точную реализацию, совместимую с RoPE конкретной LLM, проверить тестами.
- Способ выбора представления вопроса/варианта (последний токен блока, завершающий маркер, pooling и т. п.) должен быть **единым, явно заданным и версионируемым**. Не менять его незаметно между моделями.

При реализации **проверить фактическую поддержку** пользовательской block-causal attention mask и `position_ids` выбранным attention backend (`Transformers`/PyTorch), включая производительность и доступность градиентов для QLoRA. Оптимизация не должна менять семантику внимания. Полезны проверки инвариантности: в режиме независимых вариантов изменение одного варианта не должно менять представления остальных; аналогично для чужих вопросов. Сравнение с эталонными раздельными forward — один из способов тестирования.

**Не закладывать сейчас дополнительные режимы внимания без экспериментальной необходимости.**

## 6. Унифицированные признаки и feature cache

Головы работают с **одним согласованным типизированным представлением признаков**, независимо от того, пришли тензоры из кэша или от LLM.

Концептуально данные могут включать:

- token-level память контекста **последнего слоя** — `[T, D]`, если нужна Joint/Cross-Attention;
- векторы вопросов для **запрошенных слоёв** — `[Q, R, D]`;
- векторы вариантов для соответствующих вопросов — переменное число вариантов, логически `[Q, K, R, D]`;
- маски/индексы/границы для неодинаковых `T`, числа вопросов и `K`, а также нужные метаданные примера.

Здесь `R` — **число выбранных слоёв**, а не всегда все слои LLM. Конкретный формат ragged/padded батча выбрать при реализации. Не заставлять простую Pointer/MoE Head читать полный контекст, а Joint Head — получать ненужные слои.

**Три режима доступа к признакам:**

| Режим | Поведение |
|---|---|
| `cache_only` | Использовать только совместимые данные из кэша; если необходимых признаков нет — явная ошибка. **Backbone не загружается.** |
| `cache_or_compute` | Использовать кэш, недостающее вычислить загруженным backbone, по необходимости сохранить. |
| `compute` | Вычислять через backbone непосредственно, без чтения кэша. |

Также нужна **отдельная команда подготовки признаков** (условно `prepare_features`) для выбранного набора, split и необходимых типов/слоёв. В основной работе с frozen backbone предпочтительно предварительно кэшировать признаки и обучать голову без загруженной LLM.

**Важная граница ответственности:** `Dataset`/`collate_fn` могут читать и упаковывать CPU-данные, но **не следует выполнять GPU-forward backbone внутри DataLoader workers**. Проверку/получение отсутствующих GPU-признаков выполнять в основном процессе через отдельный feature provider. Требования голов к признакам должны определяться явно и проверяться до обучения.

**Кэш составной, пополняемый:**

- Дешёвые векторы вопросов/вариантов нужных слоёв можно хранить для всего набора.
- Дорогой token-level контекст последнего слоя — отдельно, при необходимости сначала только для pilot или нужных split.
- Для выбранной версии Adaptive Layer Readout рабочий пресет слоёв — **`{9, 18, 27, 36}`**, причём смешиваются **только векторы вопросов/вариантов**; контекст для Cross-Attention остаётся с последнего слоя. Не кэшировать полные токенные представления с четырёх слоёв без отдельного обоснования.
- Один и тот же кэш может использоваться разными головами. Не плодить копии полных hidden states на каждый run или вложенную train-подвыборку.

**Совместимость кэша:** рядом с данными хранить manifest/идентификатор, зависящий от всего, что **реально меняет представления**: конкретная ревизия весов и tokenizer, параметры загрузки/квантизации и вычисления, источник и ID данных, подготовка/токенизация входов, длины/обрезка, attention mask, position IDs, выбор токенов/маркеров/ pooling, извлекаемые слои, версия extractor и точность хранения. При несовпадении не использовать кэш молча. Удачный подбор гиперпараметров **головы** сам по себе не должен инвалидировать backbone cache.

**При QLoRA статический кэш hidden states адаптируемой LLM для обучения использовать нельзя:** представления меняются вместе с адаптерами, и градиент не дойдёт до LoRA. Нужен живой forward/backward через backbone. Унифицированный интерфейс признаков для головы при этом сохраняется.

### Ориентиры по объёму кэша

Для **10k примеров**, условно **1 вопрос + 4 варианта**, Qwen hidden size **2560**, хранение **FP16/BF16** (2 байта/значение), без накладных расходов:

| Состав кэша | Примерный объём |
|---|---:|
| Вопрос + варианты, только последний слой | **0,24 ГиБ** |
| Вопрос + варианты, 4 выбранных слоя | **0,95 ГиБ** |
| Token-level контекст последнего слоя, в среднем 512 токенов | **24,4 ГиБ** |
| Token-level контекст последнего слоя, в среднем 1024 токена | **48,8 ГиБ** |

Последние две строки — **только контекст**, поверх компактного кэша. Это оценки, а не измерения OpenJevData; общий контекст может переиспользоваться несколькими вопросами, и объём зависит от реальной схемы данных. **До массовой экстракции** измерить распределение token lengths и числа вариантов по выбранным примерам, оценить диск и время. Кэш может быть больше VRAM: считывать нужные части с SSD батчами. Формат хранения/шардирование/mmap выбрать по реальным требованиям, без преждевременного усложнения.

## 7. Модели: интерфейс и композиция

Разделять:

1. **Backbone / feature provider** — формирует нужные hidden states и решает, откуда их брать.
2. **Readout** — выбирает или смешивает представления слоёв (например, Last Layer или Adaptive Layer).
3. **Head** — преобразует признаки вопроса, вариантов и при необходимости контекста в оценки вариантов.
4. **Training/evaluation** — считает loss и метрики, независимо от конкретной головы.

Предпочтительно, чтобы decision-модель имела единый смысловой контракт:

```text
FeatureBatch → DecisionModel(readout, head) → scores + optional auxiliary losses
```

Учитывать **переменное число вопросов/вариантов**; padding и маски не должны приводить к обучению или оценке несуществующих вариантов. Для MoE могут понадобиться вспомогательные loss (например, балансировка экспертов): тренер должен уметь их учитывать без знания деталей архитектуры.

**Композиция нужна, но умеренная:**

- Сначала каждая идея проверяется отдельно на сопоставимом baseline.
- После положительных результатов допускаются сочетания: Adaptive Readout + Joint, Adaptive + MoE, рекуррентные Joint-блоки, MoE внутри составной головы и т. п.
- Использовать переиспользуемые модули (`nn.Module`), а не переписывать модель целиком для каждой комбинации.
- **Не пытаться разрешить произвольное соединение любых блоков в любом порядке.** Если для новой исследовательской комбинации нужно специальное взаимодействие, допустим отдельный составной модуль.
- Композиция описывается типизированным конфигом, собирается фабрикой и сохраняется стандартным механизмом весов.
- Trainer **не знает**, какая из архитектур внутри; работает с единым выходом модели.

## 8. Обучение, QLoRA и оптимизации

- **Свой небольшой training loop на PyTorch + Hugging Face Accelerate.** Accelerate использовать для технической обвязки (device placement, mixed precision, gradient accumulation и при необходимости нескольких GPU), **не** как замену PyTorch. Не использовать HF `Trainer` как обязательную основу: для кастомных decision heads и масок он может быть неудобен.
- Параметры оптимизации, seed, обработка данных, количество шагов/эпох и правила выбора checkpoint задаются конфигом, логируются и воспроизводятся.
- Для frozen режима при готовом кэше backbone не должен занимать VRAM. Перед сравнением архитектур проверять одинаковость входных представлений и честность бюджета обучения; не смешивать результаты с существенно разной вычислительной стоимостью без оговорки.
- Для будущего QLoRA базовый путь — **Transformers + PEFT + bitsandbytes**, backbone в 4-bit (рабочая идея — NF4) и LoRA-адаптеры, плюс градиенты через LLM к обучаемым адаптерам; при 8 ГБ VRAM ориентироваться на microbatch 1, gradient accumulation и gradient checkpointing, но параметры подтвердить тестом.
- **Unsloth** — перспективная **опциональная оптимизация** QLoRA по скорости/VRAM, а не обязательная зависимость. Перед использованием проверить: (а) наши block-causal masks и position IDs; (б) извлечение нужных hidden states; (в) прохождение градиента от decision head к LoRA; (г) фактическую VRAM/скорость и соответствие результатов обычному пути. Нельзя без проверки заменить им стандартную реализацию.
- Первый этап не требует распределённого обучения. Не добавлять сложные оркестраторы и HPO-инфраструктуру без потребности.

## 9. Checkpoints и восстановление

Различать два назначения:

**Model checkpoint** — для загрузки лучшей обученной модели при evaluation/benchmark/инференсе. Содержит обучаемые веса и достаточные для сборки метаданные/конфигурацию, **без optimizer state**.

**Training checkpoint** — для продолжения прерванного обучения. Дополнительно содержит состояния optimizer, scheduler, random generators, текущие шаг/эпоху и, если требуется точное возобновление, состояние sampler/DataLoader и другие элементы training loop. Просто восстановить модель и номер шага — недостаточно для точного resume.

**Политика сохранения:**

- Короткие frozen-head эксперименты: обычно достаточно **`best`** по заранее выбранной validation-метрике; можно полностью отключить сохранение весов для отладочных прогонов.
- Длинные эксперименты и QLoRA: **`best` + `latest`**, где `latest` — перезаписываемое полное состояние для resume. `best` обновлять при улучшении validation, `latest` — периодически (по времени/шагам, без навязывания одной частоты всем задачам).
- Не хранить бесконечную историю промежуточных checkpoints без специальной исследовательской причины. Сохранение делать безопасным относительно прерванной записи (временный файл/каталог и атомарная публикация там, где это возможно).

**Состав и формат:**

- Обучаемые `nn.Module` — `state_dict`, веса в **`safetensors`**.
- **Frozen pretrained LLM не сохранять повторно**: хранить точную ссылку и ревизию исходных весов. Нельзя бездумно записывать `state_dict()` составной модели со всеми 4B frozen-параметрами.
- Для LoRA использовать стандартное сохранение адаптеров **PEFT**; readout/head сохранять отдельно. В будущей составной модели сохранять все её **обучаемые** части, включая слоты, routing и прочее.
- Полная конфигурация модели (`config.json`) и метаданные (`metadata.json` или аналог) должны позволять узнать структуру, происхождение и совместимость checkpoint: версия схемы, run ID, Git commit, backbone revision, step, validation-метрика и др.
- Сложный `trainer_state` допускается хранить средствами PyTorch/Accelerate; загружать pickle-based training state только из доверенного источника.
- Загрузка: **десериализация typed config → сборка модели → загрузка весов**. Несовместимую архитектуру/размеры параметров выявлять явно; не маскировать их бездумным `strict=False`.
- Для старых архитектур допустимо восстановление старой версии репозитория из Git вместо поддержки всех старых checkpoints текущим кодом.

Checkpoints и большие feature caches остаются **локальными**; они **не входят** в согласованный резервный бэкап MLflow. Это сознательный компромисс: при потере диска данные о результатах в облаке останутся, а локальные веса/кэши могут потребовать повторного создания.

## 10. Experiment tracking и связь запусков

**Выбор: локальный MLflow** с **SQLite** как backend store, локальным хранилищем небольших артефактов и **локальным веб-интерфейсом**. Не DagsHub и не W&B как основной трекер: важны автономность, просмотр **всех** запусков локально и отсутствие лимита облачного тарифа на приватные эксперименты.

В MLflow фиксировать:

- Полный resolved config; архитектуру и режим frozen/QLoRA.
- Git commit и состояние кода, lockfile/окружение, устройство и существенные runtime-параметры.
- Dataset/split/manifest IDs, seed, backbone/tokenizer revision, feature cache/extraction config.
- Train/validation метрики во времени, лучшие значения, итоговую оценку, метрики по категориям, по возможности время/VRAM.
- Теги/группировку для сравнения архитектур, объёмов данных, seeds и режимов.

**Разные задачи — разные связанные runs**: `train`, `evaluate`, `benchmark` (при необходимости отдельно feature extraction). Оценка, проведённая позже, фиксирует **собственные** code revision, протокол и окружение и указывает `source_train_run_id` и **хеш фактически загруженных весов** (для составного checkpoint — однозначный manifest/hash набора файлов). Нельзя считать evaluation тем же запуском только потому, что используется та же модель.

Не загружать checkpoints, датасеты и большие кэши в MLflow/cloud «заодно». Для короткой отладки можно отключать полноценный tracking; существенные удачные **и неудачные** эксперименты сохранять, поскольку отрицательные результаты важны для исследования.

## 11. Резервное копирование MLflow

**Согласованный вариант:** локальные MLflow/SQLite + **ручная команда** (условно `make backup`), которая создаёт резервные копии **одновременно в Google Drive и Cloudflare R2** через **`rclone`**.

Требования:

- Сохранять **согласованный снимок SQLite** штатным механизмом backup SQLite, а не просто копировать открытую `.db` как обычный файл.
- Добавлять необходимые **небольшие артефакты MLflow** (например, конфигурации и отчёты), но исключать checkpoints и hidden-state cache.
- Отправлять бэкап **в оба независимых облачных хранилища**, сообщать об ошибках каждого; сохранять предыдущие версии/снимки, а не слепо перезаписывать единственную копию.
- Предусмотреть понятное **восстановление** и хотя бы проверку, что архив/снимок пригоден для восстановления. Следить, чтобы снимок DB и копируемые небольшие артефакты представляли согласованное состояние, насколько это необходимо.
- **Расписание не обязательно**: пользователь запускает резервирование по команде. `rclone` — внешняя операция, не часть обучения и не зависимость моделей.

**Cloudflare R2 — просто объектное облачное хранилище, не облачный MLflow UI**. Google Drive и R2 используются для бэкапов, а не для основной базы экспериментов. Конкретные аккаунты, remote names, авторизацию и скрипт резервирования агент настраивает отдельно, не зашивая секреты в репозиторий.

## 12. Минимальные проверки перед массовыми экспериментами

Сначала получить **один полностью рабочий вертикальный сценарий**: данные → извлечение признаков / кэш → простая Pointer Head → обучение → validation → MLflow → best checkpoint → отдельный evaluation с привязкой к train. Затем добавлять исследовательские головы.

Проверить как минимум:

1. Корректность размерностей, масок и потерь при **разном числе вопросов и вариантов**; отсутствие вклада padding в loss/метрики.
2. Совпадение `cache_only` и `compute` на одинаковых frozen входах **с учётом допустимой численной погрешности хранения**; отсутствие непреднамеренного смешивания несовместимых кэшей.
3. Изоляцию вопросов и независимых вариантов; корректность position IDs и причинного внимания для обоих согласованных режимов.
4. Работу обучения **без загруженной LLM** в cache-only и корректность GPU-forward вне DataLoader workers.
5. Сохранение и загрузку `best`, полноценный resume из `latest`, связь MLflow train/eval по run ID и хешу весов.
6. Реальные VRAM и время полного training step, прежде чем выбирать большие контексты, QLoRA и сложные комбинации.
7. Воспроизводимость split, настроек экстракции, метрик при фиксированном seed (насколько позволяют backend и недетерминированные операции).

## 13. Что намеренно оставлено агенту / на последующие этапы

**Не требуется решать заранее:**

- Точные имена классов, структуру отдельных модулей, формат ragged batches и публичный Python API.
- Конкретный формат/шардирование кэша (`safetensors`, mmap, Arrow и т. п.) — выбирать по профилированию и удобству.
- Точные версии библиотек и compatibility fixes под RTX 5050 — закрепить после проверки.
- Конкретные training hyperparameters, интервалы validation/checkpoint, `early stopping`, смешивание soft/hard targets и реализацию loss — задавать экспериментальными конфигами, не подменяя ими требования исследования.
- Итоговый источник и размер `research_v1`, число слоёв для другого backbone, точные маркеры извлечения, максимальную длину контекста — решить после разведки данных и минимальных тестов.
- Использование Unsloth, специфического attention backend, сверхсложных методов ускорения — только после проверки совместимости и выигрыша.
- Произвольные архитектурные комбинации, полноценную библиотеку опубликованных моделей, distributed training, крупный HPO, продакшен-сервинг и загрузку моделей на Hugging Face.

**Принцип реализации:** брать минимально достаточные стандартные инструменты, явно сохранять научно значимые настройки, обеспечивать честность сравнений и расширяемость для новых голов. Не превращать исследовательский репозиторий в инфраструктурный фреймворк до появления реальной потребности.
