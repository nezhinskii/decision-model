# Adaptive Layer Readout для Jev-like моделей

**Статус:** рабочая концепция третьего направления исследования, 17.10.2026. Приоритет — дополнительное исследование и возможный входной модуль для других голов, а не самостоятельная претензия на изобретение layer mixing. Основная версия: **question-conditioned смешивание представлений вопроса и его вариантов; контекст для Cross-Attention — только из последнего слоя**.

## Часть I. Как пришли к выбранной постановке

### 1. Исходная проблема

Jev-like модель за один проход decoder LLM обрабатывает общий контекст и один или несколько вопросов, каждый с произвольным набором вариантов. Голове нужны векторы вопросов/вариантов; в сложных головах также token-level представления контекста. В большинстве рассмотренных простых реализаций их берут с **последнего слоя**.

Но pretrained LLM обучалась в основном авторегрессионному предсказанию текста, а не предоставлению оптимальных векторов для типизированного decision readout. Промежуточные слои могут содержать признаки, доступ к которым из последнего слоя затруднён. Отсюда первая идея: использовать несколько глубин backbone, не добавляя ему проходов и не изменяя его веса.

**Оговорка:** не следует априори утверждать, что «полезные признаки теряются» или что ранний слой «отвечает за факты», а поздний — «за логику». Проверяем только полезность комбинации конкретных представлений для downstream-задачи.

### 2. Референсы и граница новизны

| Работа / система | Что действительно релевантно | Следствие для нашей идеи |
|---|---|---|
| [ELMo, Peters et al., NAACL 2018](https://aclanthology.org/N18-1202/) | *ScalarMix*: обучаемая, общая для downstream-задачи комбинация представлений разных глубин. | **Static Layer Mixing давно известен**; удобный почти бесплатный контроль. |
| [HIRE, Yang & Zhao, 2019](https://arxiv.org/abs/1911.01940) | Извлечение комплементарных представлений разных слоёв pretrained LM с входозависимыми компонентами. | **Динамический выбор слоёв тоже не новый математический принцип**. Не нужны тяжёлые BiGRU/fusion-подсети из этой работы. |
| [DWAtt, ElNokrashy et al., LREC-COLING 2024](https://aclanthology.org/2024.lrec-main.417/) | Depth-wise attention и layer fusion для классификации, включая сравнения при сходных бюджетах параметров; эффект на малоразмерных обучающих выборках. | Ближайший общий ML/NLP-ориентир: сочетание слоёв для decision-подобных задач изучено; сложный attention здесь необязателен. |
| [Kev](https://github.com/jaredpalmer/kev), [CLEF](https://huggingface.co/Cloudflare/clef/blob/main/joint_schema_model.py) | Рассмотренные стандартные decision heads используют прежде всего итоговые скрытые представления backbone. | Последний слой + обычная голова — естественный Jev-like baseline, но не универсальная характеристика всех реализаций. |
| [OpenJev](https://github.com/ejhshen/OpenJev) | Option Set Interactor / работа с вариантами, а не известный нам адаптивный depth-wise readout. | Не приписываем ему смешивание слоёв; в проверенных материалах прямого аналога не обнаружено. |
| [jev-recommend](https://github.com/wdlctc/jev-recommend) | Readout на промежуточных слоях для **early exit**; при достижении условия работа backbone может завершаться раньше. | Промежуточные решения в Jev-like уже есть, но **early exit ≠ layer fusion после полного прохода**. |
| [LoRA, Hu et al., 2021](https://arxiv.org/abs/2106.09685); [Releasing the Inner Jev, 2026](https://arxiv.org/abs/2610.17205) | Низкоранговая адаптация backbone; убедительный практический ориентир, что дообучение LLM может быть важнее усложнения readout. | Главный научный вопрос здесь — **layer extraction против изменения самих представлений** и их возможная взаимозаменяемость. |

**Новизна:** предложенный MLP-router не является изобретением нового механизма. Интересна **конкретная Jev-like постановка**: один контекст, произвольное число вопросов и вариантов; веса слоёв подбираются по содержимому *всей задачи выбора*; проверяется конкуренция с LoRA и совместимость с более сложными головами. Саму уникальность этой постановки нужно дополнительно проверять по literature на multiple-choice QA.

### 3. Почему Layer Readout особенно интересен на frozen backbone

При frozen LLM её последние слои **не могут адаптироваться** под нашу обучаемую decision head. Поэтому даже очень дешёвое использование внутренних состояний может улучшить качество.

При LoRA/QLoRA градиент decision loss достигает адаптеров backbone; поздние слои получают возможность создавать более подходящие финальные представления. Значит, польза смешивания **может уменьшиться или исчезнуть**. Это не гарантировано: LoRA ограничена своей параметризацией, а промежуточные признаки могут оставаться комплементарными.

Отсюда содержательная постановка для общей работы: **сравнить два способа адаптировать LLM к Jev-like решениям:**

- *Readout adaptation:* backbone frozen, обучаемся извлекать/смешивать его готовые представления.
- *Representation adaptation:* обучаем LoRA-адаптеры backbone и берём выход последнего слоя.

Это сравнение способов организации обучения, **не** строго равных по параметрам или стоимости. Если результат обещающий, отдельно проверяем, остаётся ли эффект layer mixing *после* LoRA.

### 4. Как уточняли сам механизм

**Первая версия:** вычислять веса слоёв по последнему представлению вопроса `q_last`, затем применять эти веса и к вопросу, и ко всем вариантам. Плюс — минимум параметров; минус — роутер не видит непосредственно **набор предлагаемых вариантов**, хотя они могут существенно определять характер выбора.

**Принятая версия:** добавить в роутер среднее представление вариантов последнего слоя: `Router([q_last; mean(O_last)])`. Это дешёвая перестановочно-инвариантная сводка набора; один набор весов на вопрос сохраняется. Не вводим option-specific веса: это дополнительные степени свободы, более трудная интерпретация и необязательное усложнение.

Рассматривали и более сложный depth-wise attention, отдельные веса для каждого варианта и смешивание итоговых logits разных слоёв. **Не включаем** их в первую реализацию: они меняют исследуемый механизм и потребуют лишних сравнений.

### 5. Почему отказались смешивать весь контекст теми же весами

В первоначальной схеме можно было бы смешивать **все** token-level hidden states контекста по весам вопроса:

`H_ctx_mix,i = Σ_l α_i,l H_ctx^(l)`.

Но к одному контексту может относиться много вопросов, а их `α_i` различны. Это создаёт **разные копии памяти одного контекста** для Cross-Attention. Тогда нельзя просто переиспользовать одну и ту же контекстную K/V-проекцию между вопросами; кроме того, нужно хранить token-level states контекста из всех выбранных слоёв.

**Зафиксированный компромисс:** смешиваем *только векторы вопроса и вариантов*. В Joint Latent-Option Head передаём **общую память контекста из последнего слоя**. Изначальная гипотеза о «полном смешивании контекста» тем самым сужается до адаптивного выбора признаков для decision states. Это осознанное ограничение ради стоимости и совместимости с эффективным multi-question batching.

## Часть II. Зафиксированная архитектура и первый план экспериментов

### 6. Входы, обозначения, источник hidden states

**Пример backbone:** [Qwen3-4B-Instruct-2507](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507/blob/main/config.json), `L=36` decoder-блоков, ширина `D=2560`; все числа ниже привязаны к этому примеру. Выбираем `S={9,18,27,36}` — **рабочий пресет, не установленный оптимум**. Число слоёв смешивания обозначим `R=|S|=4` (не путать с количеством вопросов).

Пример одного вопроса `i` с `K_i` вариантами:

| Объект | Размерность | Источник |
|---|---|---|
| `q_i^(l)` | `[D]` | Представление вопроса из слоя `l` |
| `o_ij^(l)` | `[D]` | Представление варианта `j` из того же слоя |
| `Q_i = stack_l q_i^(l)` | `[R,D] = [4,2560]` | Четыре выбранные глубины |
| `O_i = stack_j,l o_ij^(l)` | `[K_i,R,D]` | Те же позиции вариантов на четырёх глубинах |
| `H_ctx,b^(L)` | `[T_b,D]` | Token-level память контекста `b` **только последнего слоя**, если нужна Cross-Attention голове |

Извлекаем **одни и те же семантические позиции** вопроса и варианта во всех выбранных слоях, с одинаковыми входом, attention mask и position IDs. Важно согласовать, что именно называется выходом слоя 36: в Hugging Face `last_hidden_state` может включать финальную нормализацию decoder, а hook выхода последнего блока — нет. В данных и baseline используется **одна зафиксированная конвенция**. При необходимости применяем к извлечённым векторам детерминированную RMS-нормализацию без обучаемых параметров **во всех сравниваемых конфигурациях**, чтобы слои имели сопоставимые масштабы.

**Один проход backbone:** общий контекст и ветви вопросов/вариантов упакованы согласно Jev-like attention mask; вопросные ветви изолированы друг от друга. Не надо повторно кодировать контекст для каждого вопроса. Режим извлечения нескольких слоёв **не требует** новых проходов backbone.

### 7. Router: ровно четыре веса на вопрос

Для вопроса `i` берём последние представления:

`q_i^L ∈ R^2560`, `o_ij^L ∈ R^2560`.

Агрегируем варианты средним (для `K_i>=1`):

`m_i = (1/K_i) Σ_{j=1}^{K_i} o_ij^L`, `m_i ∈ R^2560`.

Готовим вход роутера:

`x_i = [q_i^L ; m_i] ∈ R^5120`.

Обучаем маленький MLP:

`u_i = GELU(W1 x_i + b1)`, где `W1: [128,5120]`, `b1: [128]`, значит `u_i: [128]`.

`a_i = W2 u_i + b2`, где `W2: [4,128]`, `b2: [4]`, значит `a_i: [4]`.

`α_i = softmax_over_layers(a_i) ∈ R^4`, `Σ_l α_i,l = 1`.

Пример `α_i = [0.1,0.2,0.3,0.4]`: для данного вопроса все четыре глубины вносят вклад, последний слой имеет наибольший вес. **Другой вопрос, даже к тому же контексту, получает свой вектор `α`.**

**Роутер не создаёт иерархии из четырёх голов.** Он выдаёт четыре скалярных коэффициента; сами downstream-головы и их параметры общие.

### 8. Смешивание и обычный scorer

Тем же `α_i` смешиваем *вопрос и все его варианты*:

`q̃_i = Σ_{l∈S} α_i,l norm(q_i^(l)) ∈ R^2560`;

`õ_ij = Σ_{l∈S} α_i,l norm(o_ij^(l)) ∈ R^2560`.

Здесь `norm` — одинаковое для всех режимов заранее определённое преобразование масштаба hidden states; если выбрана нормализация, **для вычисления входа роутера используем последовательно ту же конвенцию нормализации last-layer states**. Порядок вариантов не влияет на общий `α`, а выходы просто переставляются вместе с вариантами.

Для базового эксперимента — **одна и та же стандартная Pointer Head**, без Self-Attention и без MoE:

`u_i = W_pq q̃_i ∈ R^256`, `v_ij = W_po õ_ij ∈ R^256`,

`s_ij = (u_i · v_ij) / sqrt(256)`, `p_ij = softmax_j(s_i1,...,s_iK_i)`.

`W_pq,W_po: R^2560 → R^256`; два независимых Linear (без дополнительных ветвей). Masked softmax исключительно по реальным вариантам, loss — обычная cross-entropy по правильному варианту.

**Не смешиваем логиты послойных Pointer Heads**: у нас *одна* голова, а её вход — сформированное адаптивной смесью представление.

### 9. Сколько обучаемых параметров

Для `D=2560`, `R=4`, `d_router=128`, `d_score=256`:

| Компонент | Формула подсчёта | Параметры |
|---|---:|---:|
| `Linear(5120,128)` | `5120×128 + 128` | **655 488** |
| `Linear(128,4)` | `128×4 + 4` | **516** |
| **Итого router** | | **656 004 (~0,66 млн)** |
| `Pointer`: 2 × `Linear(2560,256)` | `2×(2560×256+256)` | **1 311 232 (~1,31 млн)** |
| **Frozen Adaptive Layer + Pointer** | | **1 967 236 (~1,97 млн)** |
| Frozen Last Layer + тот же Pointer | без router | **1 311 232** |
| Frozen Static Mix + Pointer | 4 обучаемых logit-веса для слоёв | **1 311 236** |

Дополнительные параметры Adaptive Layer относительно Last Layer — около `0,656 млн`. Нормализация в данном плане не обучаемая. Параметры самой LLM заморожены и **не входят** в эти числа. У LoRA-версии отдельное количество обучаемых адаптерных весов, зависящее от rank и списка целевых модулей; не приравниваем его к `0,66 млн` без явного подсчёта.

Для Static Mix используем четыре общих обучаемых логита `a∈R^4`, `α=softmax(a)`, одни и те же для любых вопросов. Никакого дополнительного MLP.

### 10. Пример с несколькими контекстами и вопросами

Пусть батч содержит `B=3` разных контекста. Число вопросов по контекстам `[3,1,2]`, а число вариантов для шести реальных вопросов — `[4,2,5,3,4,6]`. Тогда `P=6` вопросов и `V=24` варианта; `R=4`, `D=2560`.

| Этап | Форма тензора |
|---|---|
| Извлечённые вопросы со всех выбранных слоёв | **`Q: [P,R,D] = [6,4,2560]`** |
| Извлечённые варианты | **`O: [V,R,D] = [24,4,2560]`** |
| Вопросы последнего слоя | `[6,2560]` |
| Средние варианты по каждому вопросу | `[6,2560]` |
| Конкатенация для роутера | `[6,5120]` |
| Роутер после первой Linear | `[6,128]` |
| Logits / softmax по четырём слоям | **`α: [6,4]`** |
| Веса для реальных вариантов (индексы их вопросов) | `[24,4]` |
| Смешанные вопросы и варианты | `[6,2560]` и `[24,2560]` |
| Pointer-проекции | `[6,256]` и `[24,256]` |
| Итоговые logits вариантов | `[24]`, сегментированные по вопросам |
| Общая контекстная память *для Latent Head* | `[3,T_max,2560]` с маской по настоящим `T_b` |

Храним `option_to_question[V]`, а для внимания к контексту — `question_to_context[P]`. Для суммирования/усреднения вариантов используем `scatter_add`/segment-reduce и деление на `K_i`; затем выбираем `α[option_to_question]`. **Padding вариантов не нужен**: все вопросы и варианты допускают уплощённую упаковку; ограничение по маскам относится к backbone или более сложным головам.

Псевдокод вычислений после кэшированного backbone (без boilerplate):

```python
# q_layers: [P,4,2560], o_layers: [V,4,2560]
# option_to_question: [V], counts: [P]
q_layers = normalize(q_layers)
o_layers = normalize(o_layers)
q_last, o_last = q_layers[:, -1], o_layers[:, -1]
o_mean = segment_mean(o_last, option_to_question, n_segments=P)  # [P,D]
alpha = softmax(router(cat(q_last, o_mean)), dim=-1)               # [P,4]
q_mix = (q_layers * alpha[:, :, None]).sum(dim=1)                 # [P,D]
o_mix = (o_layers * alpha[option_to_question, :, None]).sum(dim=1)  # [V,D]
logits = pointer(q_mix[option_to_question], o_mix)                 # [V]
# grouped cross-entropy по реальным вариантам каждого вопроса
```

`segment_mean` — любая корректная GPU-векторизованная групповая операция; самостоятельный trainable pooling не нужен.

### 11. Совместимость с двумя другими направлениями

**A. Joint Latent-Option Head (первая идея).**

После readout получаем `q̃:[P,2560]`, `õ:[V,2560]` и подаём в ранее зафиксированные проекции головы `2560→768`. Формируем для каждого вопроса `[q̃_i, E_1..E_64, õ_i1..õ_iK]`; два блока `Self-Attn → Cross-Attn → FFN`; общий Pointer scorer `768→256`.

Для Cross-Attention используем `H_ctx^(36): [B,T_max,2560]`, проецируемый в `768`. **Не применяем вопросозависимое `α_i` к контекстной памяти.** Тогда на каждом блоке все вопросы одного контекста обращаются к **одним и тем же K/V**, которые можно вычислить и переиспользовать один раз на контекст, как было предусмотрено архитектурой. Представления вопроса/вариантов и контекста могут быть получены из разных комбинаций слоёв: обучаемые проекции согласуют пространства, но качество этой комбинации должно проверяться.

**B. Question–Option MoE (вторая идея).**

Вместо исходных `q/o` из последнего слоя подаём `q̃/õ` на уже зафиксированные входные проекции `2560→512`. Внутри MoE ничего не меняем: 8 MLP-экспертов `512→1024→512`, Top-2 по варианту, стандартный общий Pointer, Set-Aware отдельно. Здесь вообще не требуется token-level память контекста.

**Важно:** обе интеграции — *возможные будущие комбинации*, а не часть первой абляции Adaptive Layer Readout. Взаимодействие улучшений нельзя предполагать аддитивным: сложная голова уже может компенсировать слабость исходных признаков; обучать объединённые системы имеет смысл лишь после независимых пилотов.

### 12. Минимальный экспериментальный протокол

Одна и та же LLM, dataset split, обработка входа, token positions, scorer `Pointer`, CE, правило усреднения loss по **реальным вопросам**. Для frozen-вариантов заранее **один раз кэшируем одинаковые `Q/O` выбранных слоёв**, затем независимо обучаем головы с нуля. Не допускаем отличий в количестве/сложности вопросов между конфигурациями.

| Обозначение | Backbone | Readout | Что выясняем |
|---|---|---|---|
| **A. Last** | Frozen | Только слой 36 + Pointer | Стандартная точка отсчёта |
| **B. Static** | Frozen | `α` — четыре общих обучаемых веса + Pointer | Помогает ли использование нескольких слоёв вообще |
| **C. Adaptive** | Frozen | `Router([q_last; mean(O_last)])` + смешивание + Pointer | Даёт ли пользу **именно зависимость весов от вопроса/набора вариантов** |
| **D. LoRA Last** | LoRA/QLoRA | Последний слой + Pointer | Может ли адаптация самого backbone заменить layer mixing |
| **E. LoRA Adaptive** *(необязательно)* | LoRA/QLoRA | Adaptive Mix + Pointer | Сохраняется ли эффект mixing **после** адаптации backbone |

**Первый этап (дёшево): A, B, C.** Это две смысловые абляции, обучаемые на одном кэше. Сравнение `C−B` обязательно, если делаем утверждение про пользу *адаптивности*, а не просто про преимущества нескольких слоёв. Первые результаты допустимо оценивать на одном seed, основные выводы — желательно подтвердить несколькими seeds.

**Второй этап (дороже): D**, только при наличии ресурсов, **без обязательного E**. `C` и `D` сравнивают два подхода, а не изолированную разницу одного модуля: различаются trainable params, backward и затраты. Поэтому вместе с качеством нужны фактические обучение/время/VRAM/число trainable params. Без **E** нельзя заключить, что после LoRA от mixing «нет пользы»: это останется непроверенной гипотезой.

**Метрики:** accuracy (основная), multiclass Brier score (калибровка; при необходимости ECE), latency полной системы и головы отдельно, GPU memory, trainable params и стоимость обучения. Сравниваем по нескольким типам стандартных Jev-like задач, не только по среднему на одной тематике. Подбор обучения — сопоставимый бюджет, не обязательно буквально одинаковый LR для LoRA и маленького MLP.

**Контроль интерпретации:** если `C>A`, это ещё не доказывает динамическую пользу (`B` мог показать то же). Если `C>D`, это не означает, что readout «лучше LoRA» при равной стоимости: стоимости различаются. Если `D>C`, это не делает mixing бесполезным — он мог быть выгоднее по цене обучения. Если `E≈D`, это поддерживает отсутствие *дополнительного* эффекта mixing **в выбранном режиме и данных**, но не универсальный вывод обо всех адаптерах/задачах.

### 13. Реализация при RTX 5050 8 ГБ: память и кэш

Для frozen-эксперимента не нужно сохранять все token-level states со всех слоёв. Извлекаем только **четыре вектора на вопрос и четыре на вариант**, затем при необходимости отдельно token-level контекст **последнего** слоя для Joint Latent Head.

Пример без учёта накладных расходов: `R=4`, `D=2560`, FP16 — **20 КиБ на один вопрос или один вариант**. Для показанного батча `P+V=30`: `(30×4×2560×2)` байт ≈ **0,59 МиБ**. Полные представления *одного* контекста `T=2048`, `D=2560` занимают ≈ **10 МиБ за слой**, или **40 МиБ на четыре слоя**; поэтому без необходимости контекст на четырёх глубинах **не кэшируем**.

В идеале сохранять выбранные выходы **по мере прохождения соответствующего слоя** (hooks или специализированный extractor), а не требовать `output_hidden_states=True` для всех 36 слоёв с хранением всех токенов. После извлечения frozen LLM можно выгрузить и обучать лёгкую голову на кэшированных данных. Кэшировать в формате FP16/BF16, фиксировать точный checkpoint, входную схему, positions и нормализацию; train/val/test не пересекаются.

В режиме QLoRA представления **зависят от обучаемых адаптеров**, поэтому такой фиксированный кэш нельзя переиспользовать для обучения `D/E`. Нужен forward/backward через backbone, существенно больше VRAM и меньшие microbatches/gradient accumulation. Для `D` не требуется держать выходы всех четырёх слоёв; для `E` требуется, поэтому объединённый режим дороже и не входит в минимальный план.

На инференсе layer mixing не добавляет проходов backbone, но требует удерживать/извлечь несколько промежуточных векторов и выполнить лёгкий router. Это **не нулевая** накладная стоимость; для полного end-to-end latency измеряем реальную реализацию.

### 14. Что зафиксировано и что оставлено открытым

**Зафиксировано для первой реализации:** frozen Qwen3-4B как стартовый backbone; выбранные слои `{9,18,27,36}`; `D=2560`; веса слоя по `q_last` и среднему `O_last`; MLP `5120→128→4`; **одни веса на весь вопрос и все его варианты**; смешивание только `q/o`; стандартный Pointer `2560→256`; CE; минимальные frozen-сравнения **Last / Static / Adaptive**; LoRA Last — следующий этап.

**При интеграции:** контекст для Cross-Attention **только из последнего слоя**; те же K/V переиспользуются всеми вопросами контекста; для MoE — смешанные представления просто заменяют исходные входы, без изменения экспертной архитектуры.

**Пока открыто:** точный набор слоёв для другого backbone; оптимальная нормализация и инициализация весов при сохранении честного baseline; насколько Static/Adaptive улучшит accuracy или калибровку; сохранится ли преимущество после LoRA; стоит ли смешивать входы Joint Latent/MoE при положительном результате standalone; выбор бенчмарков и окончательная значимость/новизна относительно более широких работ по multiple-choice layer fusion.

**Главная гипотеза:** *адаптивный выбор глубины представлений для конкретного Jev-like вопроса и набора вариантов может компенсировать часть недостатков frozen decoder при небольшой стоимости; дальнейшее LoRA-сравнение позволяет выяснить, является ли этот выигрыш альтернативой адаптации самого backbone или полезным дополнением к ней*.
